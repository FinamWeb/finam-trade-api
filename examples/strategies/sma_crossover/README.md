# Пересечение SMA 9/30

Стратегия только в лонг на пересечении скользящих средних, реализованная по
одному разу на каждый язык против соответствующего опубликованного SDK Trade API.

| Язык | Реализация | SDK |
| --- | --- | --- |
| Python | [`python/`](python/) | `finam-sdk` |
| Node.js | [`node/`](node/) | `@finam/trade-api` |

## Быстрый старт: проверка истории только на чтение

Запустите одну из реализаций из корня репозитория. Режим проверки
аутентифицируется, загружает исторические свечи, печатает последние
подтверждённые значения SMA и завершается. Он не читает счёт, не открывает
поток и не выставляет заявку.

```sh
# Python 3.10+ и uv
cd examples/strategies/sma_crossover/python
uv sync --locked
TRADE_API_SECRET=... uv run python main.py --symbol SBER@MISX --check
```

```sh
# Node.js 20+
cd examples/strategies/sma_crossover/node
npm ci
TRADE_API_SECRET=... npm start -- --symbol SBER@MISX --check
```

Ожидаемый вывод начинается так:

```text
History check passed: close=... sma9=... sma30=... signal=...
```

Эта страница описывает саму стратегию: правило, работу со свечами и защитные
проверки, которые обязана соблюдать каждая реализация. У каждого языкового
каталога свой README только про установку, запуск и тесты для этой экосистемы.

## Правило

- **Вход:** предыдущая SMA 9 ≤ предыдущей SMA 30, и текущая SMA 9 > текущей SMA 30.
- **Выход:** предыдущая SMA 9 ≥ предыдущей SMA 30, и текущая SMA 9 < текущей SMA 30.
- Средние считаются по ценам закрытия закрытых свечей.
- Пока окно в 30 свечей прогревается, сигнал не выдаётся.
- Сигнал выдаётся один раз на свече пересечения, а не на каждой свече, пока одна
  средняя остаётся выше другой.

Для обнаружения пересечения нужны два соседних значения SMA 30, поэтому правилу
требуется 31 закрытие, прежде чем оно сможет выдать первый сигнал.

## Поток данных и исполнения

```text
market_data.Bars ───────┐
                        ├─> закрытые свечи ─> SMA 9/30 ─> сигнал
market_data.SubscribeBars┘                                │
                                                         ├─> лог dry-run
auth.TokenDetails ─> ID счёта ────────────────────────────┤
accounts.GetAccount ──────────────────────────────────────┤
orders.PlaceOrder <───────────────────────────────────────┘
```

Каждый SDK уже предоставляет все нужные операции. Реализация не должна
импортировать сгенерированные заглушки напрямую или строить собственный
транспорт.

## Как обрабатываются закрытые свечи

Самая новая историческая или потоковая свеча держится в ожидании. Обновления с
той же меткой времени заменяют её. Только свеча с более поздней меткой времени
подтверждает, что ожидающая свеча закрылась, и тогда та передаётся в расчёт SMA.

Исторические свечи прогревают средние без выставления заявок.

## Защитные проверки

По умолчанию dry-run. Чтение рыночных данных и печать сигналов не смотрят на
счета токена и никогда не должны читать счёт или выставлять заявку. Настоящая
торговля требует явного флага согласия. На старте стратегия получает ID счёта
через `AuthService.TokenDetails` и отказывается торговать, если токену
доступно не ровно один счёт.

Перед отправкой заявки:

- вход требует, чтобы текущая позиция была ровно нулевой;
- выход требует положительной длинной позиции;
- количество на выходе ограничено текущей длинной позицией, что исключает
  открытие шорта;
- свеча сигнала даёт детерминированный клиентский ID заявки.

Используйте для этого примера выделенный счёт. API отдаёт агрегированную
позицию по инструменту, поэтому процесс не отличит позицию, открытую вручную, от
открытой стратегией. Настоящие рыночные заявки также несут ценовой риск и риск
ликвидности.

## Настройки

Каждая реализация читает одни и те же настройки из флагов или переменных
окружения. Их задаёт один общий файл в корне репозитория, и каждый рецепт `just`
загружает его автоматически:

```sh
# Из корня репозитория
cp .env.example .env
# Отредактируйте .env, затем:
just run-strategy-python sma_crossover --check
just run-strategy-node sma_crossover --check
```

Сами программы никогда не читают `.env`. Чтобы запустить одну из них напрямую из
языкового каталога, сначала экспортируйте файл:

```sh
set -a
source ../../../../.env
set +a
```

Репозиторий игнорирует `.env`; никогда не коммитьте настоящие секреты.
Переменные, уже экспортированные в оболочке, имеют приоритет над файлом.

| Переменная окружения | Обязательна | По умолчанию |
| --- | --- | --- |
| `TRADE_API_SECRET` | Да, если не передан `--secret` | — |
| `TRADE_API_SYMBOL` | Да, если не передан `--symbol` | — |
| `TRADE_API_TIMEFRAME` | Нет | `M5` |
| `TRADE_API_QUANTITY` | Нет | `1` |
| `TRADE_API_LOG_LEVEL` | Нет | `INFO` |

Инструменты записываются как `ticker@mic`, например `SBER@MISX`. Поддерживаемые
таймфреймы: `M1`, `M5`, `M15`, `M30`, `H1`, `H2`, `H4`, `H8`, `D`, `W`, `MN` и
`QR`.

## Smoke-тест только на чтение

Каждая реализация предлагает режим проверки, который аутентифицируется,
загружает исторические свечи, считает последние подтверждённые значения SMA,
печатает одну строку и завершается, не открывая поток, не читая счёт и не
выставляя заявку:

```text
History check passed: close=... sma9=... sma30=... signal=...
```

## Рамки

Это учебный материал, а не production-система торговли. Приложениям на его
основе всё равно нужны постоянное состояние, переподключение потока, добор
пропущенных свечей, мониторинг, лимиты риска, сверка и операционный контроль,
соответствующие их задаче.
