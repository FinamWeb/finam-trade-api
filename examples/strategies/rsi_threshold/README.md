# Пороги RSI 14

Стратегия только в лонг на RSI, которая покупает слабость и продаёт силу,
реализованная по одному разу на каждый язык против соответствующего
опубликованного SDK Trade API.

| Язык | Реализация | SDK |
| --- | --- | --- |
| Python | [`python/`](python/) | `finam-sdk` |
| Node.js | [`node/`](node/) | `@finam/trade-api` |

## Быстрый старт: проверка истории только на чтение

Запустите одну из реализаций из корня репозитория. Режим проверки
аутентифицируется, загружает исторические свечи, печатает последний
подтверждённый RSI и завершается. Он не читает счёт, не открывает поток и не
выставляет заявку.

```sh
# Python 3.10+ и uv
cd examples/strategies/rsi_threshold/python
uv sync --locked
TRADE_API_SECRET=... uv run python main.py --symbol SBER@MISX --check
```

```sh
# Node.js 20+
cd examples/strategies/rsi_threshold/node
npm ci
TRADE_API_SECRET=... npm start -- --symbol SBER@MISX --check
```

Ожидаемый вывод начинается так:

```text
History check passed: close=... rsi=... average_gain=... average_loss=... signal=...
```

Эта страница описывает саму стратегию: правило, работу со свечами и защитные
проверки, которые обязана соблюдать каждая реализация. У каждого языкового
каталога свой README только про установку, запуск и тесты для этой экосистемы.

## Правило

Индекс относительной силы сравнивает средний рост со средним падением за
последние 14 закрытых свечей. Низкое значение означает, что в окне преобладали
падения, высокое — что росты.

- **Вход:** RSI ниже **0.2**, пока стратегия вне позиции.
- **Выход:** RSI выше **0.8**, пока стратегия держит позицию.
- Средний рост и среднее падение по Уайлдеру считаются и логируются для
  контекста. Ни одно правило не читает их напрямую; оба сравнивают отношение.
- Средние считаются по ценам закрытия закрытых свечей.
- Пока средние прогреваются, сигнал не выдаётся.

Это правило возврата к среднему: оно покупает на распродаже и продаёт на
ралли — противоположность трендовому поведению в примерах SMA и MACD. Поэтому
оно может войти, пока цена ещё падает, и удерживать позицию через дальнейшее
снижение.

### Шкала: 0.2 и 0.8, а не 20 и 80

RSI часто публикуют на шкале 0–100, где эти уровни — знакомая пара
перепроданности/перекупленности **20 и 80**. Эта стратегия держит отношение на
его естественной шкале **0..1**, поэтому `0.2` и `0.8` здесь означают ровно те же
уровни. Умножьте любое залогированное значение `rsi` на 100, чтобы сравнить его с
графическим пакетом.

Реализации считают `average_gain / (average_gain + average_loss)`, что есть
обычная формула `100 - 100 / (1 + gain / loss)` в переставленном виде. Обе
совпадают всюду, но эта форма не требует особого случая для окна без падений.
Окно без ростов *и* без падений — полностью плоская цена — оставляет отношение
неопределённым; обе реализации сообщают середину `0.5`, которая лежит между
уровнями, поэтому остановившийся поток сам по себе не откроет сделку.

### Уровни, а не пересечения

Оба правила проверяют текущее значение относительно уровня. Ни одно не
сравнивает его с предыдущей свечой, поэтому RSI, остающийся ниже 0.2 десять
свечей подряд, удовлетворяет условию входа на всех десяти. Второй вход
останавливает состояние позиции, описанное в разделе
[Как отслеживается позиция](#как-отслеживается-позиция), а не правило. Это самое
важное, что нужно понять перед копированием примера: `evaluate` безопасно
вызывать в цикле, только если вызывающий код передаёт обратно свою позицию.

Два правила ещё и независимы — полосы не пересекаются, — поэтому:

- перепроданное значение при уже открытой позиции не увеличивает её;
- перекупленное значение вне позиции не является выходом;
- позицию можно держать долго, потому что цене нужно пройти от одной крайности
  до другой, прежде чем сработает выход;
- между 0.2 и 0.8 вообще ничего не происходит, какой бы ни была позиция.

### Прогрев

Средние покрывают 14 изменений цены, а первому изменению нужно ещё и закрытие
перед ним, поэтому оценке нужны **15 закрытых закрытий** — 16 свечей, потому
что самая новая ещё в ожидании. `--check` завершается понятным сообщением, если
запрошенный таймфрейм не может их дать.

Сглаживание Уайлдера несёт всю свою историю, поэтому значение зависит от того,
где средняя началась. Реализации сеют первое среднее простым средним и держат
последние 140 закрытий (десять периодов) во время потока. Этого достаточно,
чтобы посев больше не влиял заметно на новейшее значение, и перезапущенный
процесс сходился к тому же RSI.

## Поток данных и исполнения

```text
market_data.Bars ───────┐
                        ├─> закрытые свечи ─> RSI 14 ─> сигнал
market_data.SubscribeBars┘                              │
                                                       ├─> лог dry-run
auth.TokenDetails ─> ID счёта ──────────────────────────┤
accounts.GetAccount ────────────────────────────────────┤
orders.PlaceOrder <─────────────────────────────────────┘
```

Каждый SDK уже предоставляет все нужные операции. Реализация не должна
импортировать сгенерированные заглушки напрямую или строить собственный
транспорт.

## Как обрабатываются закрытые свечи

Самая новая историческая или потоковая свеча держится в ожидании. Обновления с
той же меткой времени заменяют её. Только свеча с более поздней меткой времени
подтверждает, что ожидающая свеча закрылась, и тогда та передаётся в расчёт RSI.

Исторические свечи прогревают средние без выставления заявок.

## Как отслеживается позиция

Поскольку оба правила — уровни, а не пересечения, стратегия должна знать,
держит ли она позицию. Каждая реализация хранит один флаг в памяти:

- при каждом запуске он начинается с «вне позиции», и стратегия никогда не
  присваивает позицию, которую не открывала;
- флаг следует за тем, что подразумевает исполненный сигнал: лонг после входа,
  вне позиции после выхода;
- вход, заблокированный защитной проверкой, не присваивается, поэтому стратегия
  остаётся вне позиции и может действовать на следующем сигнале;
- выход, заблокированный потому, что на счёте ничего нет, всё равно сбрасывает
  флаг — проверка только что подтвердила, что стратегия вне позиции, поэтому
  неисполненная заявка не может её «подвесить»;
- dry-run тоже устанавливает флаг, поэтому его лог чередует вход и выход вместо
  повторения входа на каждой перепроданной свече.

Флаг живёт в памяти. Перезапущенный процесс снова вне позиции, что бы ни было на
счёте. Поэтому перезапуск во время перепроданного участка откроет позицию,
которую предыдущий процесс уже открыл; в режиме исполнения это блокирует
проверка входа ниже.

## Защитные проверки

По умолчанию dry-run. Чтение рыночных данных и печать сигналов не смотрят на
счета токена и никогда не должны читать счёт или выставлять заявку. Настоящая
торговля требует явного флага согласия. На старте стратегия получает ID счёта
через `AuthService.TokenDetails` и отказывается торговать, если токену
доступно не ровно один счёт.

Перед отправкой заявки:

- вход требует, чтобы текущая позиция была ровно нулевой;
- выход требует положительной длинной позиции;
- количество на выходе ограничено текущей длинной позицией, что исключает
  открытие шорта;
- свеча сигнала даёт детерминированный клиентский ID заявки.

Используйте для этого примера выделенный счёт. API отдаёт агрегированную
позицию по инструменту, поэтому процесс не отличит позицию, открытую вручную, от
открытой стратегией. Настоящие рыночные заявки также несут ценовой риск и риск
ликвидности.

## Настройки

Каждая реализация читает одни и те же настройки из флагов или переменных
окружения. Их задаёт один общий файл в корне репозитория, и каждый рецепт `just`
загружает его автоматически:

```sh
# Из корня репозитория
cp .env.example .env
# Отредактируйте .env, затем:
just run-strategy-python rsi_threshold --check
just run-strategy-node rsi_threshold --check
```

Сами программы никогда не читают `.env`. Чтобы запустить одну из них напрямую из
языкового каталога, сначала экспортируйте файл:

```sh
set -a
source ../../../../.env
set +a
```

Репозиторий игнорирует `.env`; никогда не коммитьте настоящие секреты.
Переменные, уже экспортированные в оболочке, имеют приоритет над файлом.

| Переменная окружения | Обязательна | По умолчанию |
| --- | --- | --- |
| `TRADE_API_SECRET` | Да, если не передан `--secret` | — |
| `TRADE_API_SYMBOL` | Да, если не передан `--symbol` | — |
| `TRADE_API_TIMEFRAME` | Нет | `M5` |
| `TRADE_API_QUANTITY` | Нет | `1` |
| `TRADE_API_LOG_LEVEL` | Нет | `INFO` |

Инструменты записываются как `ticker@mic`, например `SBER@MISX`. Поддерживаемые
таймфреймы: `M1`, `M5`, `M15`, `M30`, `H1`, `H2`, `H4`, `H8`, `D`, `W`, `MN` и
`QR`. Период и оба уровня — часть правила и из командной строки не
настраиваются. `evaluate` принимает их аргументами, поэтому копия примера может
работать с другими настройками, передав их в вызове внутри `runner`:

```python
# Определено в python/strategy.py, вызывается из python/runner.py.
evaluate(closes, in_position, period=14, entry_level=Decimal("0.2"), exit_level=Decimal("0.8"))
```

```ts
// Определено в node/strategy.ts, вызывается из node/runner.ts.
evaluate(closes, inPosition, /* period */ 14, /* entryLevel */ 0.2, /* exitLevel */ 0.8);
```

Уровни должны удовлетворять `0 <= entry_level < exit_level <= 1`; всё остальное
вызывает ошибку до выдачи сигнала. Оба модуля выводят прогрев из периода,
поэтому более короткая или длинная настройка меняет, сколько свечей нужно
первому сигналу; число сообщают `required_closes` и `requiredCloses`.

## Smoke-тест только на чтение

Каждая реализация предлагает режим проверки, который аутентифицируется,
загружает исторические свечи, считает последний подтверждённый RSI, печатает
одну строку и завершается, не открывая поток, не читая счёт и не выставляя
заявку:

```text
History check passed: close=... rsi=... average_gain=... average_loss=... signal=...
```

Значения округляются до шести знаков только для вывода; правило сравнивает
полные значения.

## Что логирует dry-run

Без `--check` стратегия читает поток и пишет по одной строке на закрытую свечу
плюс предупреждение всякий раз, когда срабатывает сигнал. В этом фрагменте
распродажа опускает отношение ниже 0.2 и открывает позицию:

```text
History ready: close=100.26221594277987 rsi=0.558339
Closed bar: close=99.35551757554535 rsi=0.409960 average_gain=0.099908 average_loss=0.143794 signal=none
Closed bar: close=98.27792419044236 rsi=0.305910 average_gain=0.092772 average_loss=0.210494 signal=none
Closed bar: close=97.14548127769474 rsi=0.237647 average_gain=0.086146 average_loss=0.276348 signal=none
Closed bar: close=96.10407145930658 rsi=0.194634 average_gain=0.079992 average_loss=0.330995 signal=entry
DRY RUN: entry 2 units of SBER@MISX
```

Обе реализации выводят одинаковый текст сообщений. Python пропускает его через
`logging`, поэтому каждая строка несёт ещё метку времени, уровень и имя логгера;
Node.js печатает только сообщение. `--log-level WARNING` оставляет только строки
сигналов и заявок.

В режиме исполнения строка `DRY RUN` заменяется результатом проверки —
отправленной заявкой с её ID и статусом либо причиной, по которой заявка
пропущена.

## Рамки

Это учебный материал, а не production-система торговли. Приложениям на его
основе всё равно нужны постоянное состояние, переподключение потока, добор
пропущенных свечей, мониторинг, лимиты риска, сверка и операционный контроль,
соответствующие их задаче. В частности, отслеживание позиции живёт только в
памяти, и настоящее приложение заменило бы его сверенным постоянным состоянием.
У правила возврата к среднему без стопа также нет встроенного ответа на цену,
которая продолжает падать после входа; добавить его оставлено читателю.
